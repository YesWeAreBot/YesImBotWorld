# 聊天记录顺序、时间来源与补拉历史

修复的是两种时钟被误用为同一条会话的排序依据：平台入站 `session.timestamp` 与本机发送确认 `new Date()` 可能存在偏差。即使两个时间都是真实记录，把它们混合排序也会把回复放到提问之前。本实现不估算或扣除固定秒数，不修改原平台时间，也不回写已经进入 Bot 上下文的事件。

## 数据契约

原 `timestamp` 保留不变，增量增加可空字段：

- `timestampSource`：`platform` / `local-confirmed` / `local-observed` / `legacy-unknown`。它说明原时间是谁提供的，不负责排序。
- `observedAt`：本机接收事件或确认发送的实际时刻。历史补拉和旧记录为空；下载完媒体的时刻不冒充接收时刻。
- `timelineKey`：消息顺序键，纯数字、按数据库字符串序比较。直播事件用固定宽度的单调槽位；历史插入使用槽位之间的分数键，不消耗浮点精度。
- `orderSource`：`live` / `history` / `history-unanchored` / `legacy`。
- `platformSequence`：平台确实提供时保存群消息序号；不用普通消息 ID 猜序号。

网关在事件进入队列时领取票据，成功的外发捕获在 transport 确认时领取票据。工具发送与外发捕获通过平台、接收账号、频道和消息 ID 复用票据；经过账号一致性校验的自账号平台回声若更早到达，保留这次实际观察的位置，晚到的发送确认仍记录真实确认时间。即使关闭外部自发消息模拟，纯排序票据仍保留，不因此宣称角色自主发送。媒体下载、查昵称、入库完成次序不会改变预留顺序。同一进程的写入串行核对消息 ID，避免历史补拉和实时入站重复入库。

`channelMessages`、最近频道、频道参与者最新昵称和冷群发送守卫通过同一顺序查询。快照只陈述已经保存的记录，不声称尚未处理完的消息不存在。`formatMessageTime` 保留平台时间和本机接收时间的来源标签，`MESSAGE_ORDER_GUIDANCE` 明确不能用不同来源的时间重新推断先后。

## 补拉与边界

补拉仍然限定为最多 4 页、每页 50 条。请求前预留栅栏；按平台消息 ID 寻找与已存记录重叠的锚点，而不是用本机发送时间作为水位。若整批都有有效平台序号，按序号排序；否则使用平台自己的时间排序，同秒且无序号时只保留平台返回的相对顺序，不声称恢复了未知次序。先收集各页，再按从早到晚处理，避免逆向翻页的入库顺序污染会话。

新记录根据相邻已知消息锚点插入，并避开当前频道已占的位置；先前补拉已保存的平台序号也参与约束。锚点之后的补拉消息位于请求前的栅栏内，后来实时收到的消息不被挤到它们之前。找不到锚点、或锚点顺序与本地接收顺序冲突时，保守标记为 `history-unanchored`，放在已确认实时记录之前并显示“与本地记录先后未确认”。锚点中间夹杂但未出现在平台返回里的其他本地消息，其精确相对位置同样未知，行内有明确提示。这不是宣称平台事件一定更早，而是避免把未知历史当成刚收到的新回复。超出翻页上限且无重叠的记录不会获得虚构的精确位置。

平台时间比本机快或慢都不构成丢弃理由。平台消息 ID 去重与序号分页替代原来的混钟时间水位。有限页面仍不等于完整恢复离线期间的全部历史。

## 旧数据迁移

首次查询进行可恢复的加法迁移，仅补新顺序字段，不改正文、昵称、发送者归属、原 timestamp 或 Bot 事件流。正常旧行只能按已存 ID 恢复“入库先后”，不能追认它就是准确接收先后；显示会明确说明。旧补拉器明确留下的 `senderOrigin: unknown` 记录可识别为历史，其平台时间保留，位置按未锚定历史处理。更早没有该标记的历史与实时记录无法可靠区分，仍属于 `legacy`，不伪造缺失证据。

迁移分批写入新元数据，已有 `timelineKey` 的行不重写；进程重启后从已存最大位置继续。首次迁移需要扫描已有消息的 ID、来源和时间字段，成本与库大小有关。已持久化旧 Bot 上下文仍可能包含旧顺序认知，后续真实回读提供新的界面说明，而不是悄悄改写经历。

## 通知与免打扰

放下手机仍可感觉到允许通知频道的震动；匿名震动没有隐藏的频道、发送者或正文归属。设置免打扰仍须拿起手机并进入聊天 app 的目标频道，工具可用条件没有放宽。

频道列表和当前频道显示真实通知状态。免打扰约束主动震动和唤醒；正在打开该频道时仍能看见消息。通知设置串行保存，保存失败会报错并保持原内存状态，不能产生虚假的成功回执。显式账号级“开启”可覆盖旧频道键的免打扰例外。
