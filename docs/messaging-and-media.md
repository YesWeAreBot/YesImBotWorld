# 聊天平台与多模态

[文档目录](README.md) · [项目首页](../README.md)

消息身份、引用、表情包、图文混排、媒体发送，以及账号外部消息的处理。

## 聊天参与与消息来源

群聊消息会保留频道、发言人、实际 @、引用作者和媒体类型，包括图片请求中的有序内容。新消息还保存本条表情包、平台表情等元素的数量，区分单独发出的表情与配合文字的表意；引用和转发内部的文字、@、表情不计入外层发言。新增独立 `bot.conversation` 提示词区分群友之间的讨论、直接对 Bot 的交流和表情氛围；通知和模型唤醒不等于回复义务。参与判断仍由模型结合上下文作出，既有通知/唤醒配置保持有效。

## 多模态

消息中的**图片 / 音频 / 视频**会进入本地资产库（`basePath/assets/`，按 sha256 去重，以避免平台 URL 过期）。消息记录保存内部媒体引用，呈现给 Bot 时转换为统一的 `media:N`：名称、摘要和实际媒体内容紧邻同一标识，并保留文字与多张图片在原消息中的顺序。收藏夹引用使用完整的 `gallery:分类/文件名`，实际文件的哈希决定它对应哪个媒体和摘要，同名文件不会被直接视为同一张图。

表情包首先是会话表意，类似 emoji；画面主题不是发送者的意图，也不表示需要点评、收藏或回复。只有平台明确标记的 `sticker` / `mface`、相应图片子类型或协议专用 `marketface` 标记才按本次表情使用处理；GIF、文件名、可爱的图案或旧资产曾被当作表情，都不能把本次普通图片改判成表情包。普通图的画面摘要和表情的表达线索分别缓存，表达线索不能断言发送者的心情，也不把某张猫图固定翻译为“已读”。同一素材可以在不同消息中承担不同用途。

原生图片、摘要和每次使用的标记保留在同一媒体位置。可见新消息与回看记录共享稳定的聊天记录编号：不同消息编号使用同一素材仍是新的发言，同一消息的重复回读不算再次发送；媒体字节复用只节省上下文，不折叠真实连发表情的数量。旧冻结消息不重写，新说明通过追加事件生效。


1. **原生模态**（`bot.modalities.image/audio/video`）：声明 Bot-LLM 支持的输入能力。按 `bot.apiType` 转成对应接口的原生媒体块，并紧跟所属媒体身份，不使用“第几个附件”建立对应关系。Chat Completions 使用 `image_url` / `input_audio` / `video_url`；Responses 和 Anthropic 适配器支持图片，原生音视频暂不支持，会沿媒体降级流程尝试解释器。GIF 在有视频能力时使用视频通道，仅有图像能力时尝试转成拼帧图，并保留原媒体标识。
2. **外挂解释器**（`captioners.image/audio/video`）：按需生成并缓存与该媒体绑定的文字摘要，也可辅助原生观看；不具备原生能力时，仅呈现同一 `media:N` 的摘要并明确说明没有展开原始媒体。解释器的对话请求同样可选择 API 协议，但服务必须支持相应输入模态；当前视频或聊天式音频解释需要支持该模态的 Chat Completions 服务。audio 默认使用 `/v1/audio/transcriptions`，也可配置多模态对话。`check_msg` 的轻量预览不触发解释器；详细查看、进入会话或内容通知才按需展开。
3. **无法查看**：没有可用原始输入或解释结果时，仍保留媒体身份并明确标记无法查看。摘要属于辅助材料，不能据此补造未看到的细节。

音频输入需要 Koishi 进程的 `PATH` 中有 `ffmpeg`。原生音频、聊天式音频解释器和语音转写共用真实解码，按文件字节识别格式，再转换为单声道 16 kHz PCM16 WAV；平台将 AMR 错标成 MP3，或传入 AAC/M4A/WebM 等容器时，也不再直接把原始编码交给模型。资产文件、引用和哈希保持不变；仅模型输入使用派生 WAV。解码最多 30 秒，输入/输出各限制 20 MiB，损坏、超限或当前解码器不支持的音频明确失败，不伪装成成功听见。请求预算按转换后的 Base64 大小计算。

图片、音频和文字可以在同一条消息内交错排列，模型请求保留各自位置与 `media:N` 身份。终端仅记录待注入媒体的类型和引用；实际是否注入须查看运行洞察中的请求体：Chat Completions 的 `image_url` / `input_audio`、Responses 的 `input_image` 或 Anthropic 的 `image` 块都应位于所属媒体文字附近；接口能力和降级规则见[模型接口](model-apis.md)。文字存档与聊天归属参考只保存媒体身份和已有摘要，不据此断言模型没有收到原始媒体。媒体渲染版本随事件保存，旧上下文保持原样，新提示在新事件及正常压缩时生效。

原生输入受以下预算约束：

| 配置 | 默认值 | 作用 |
|---|---|---|
| `media.maxAttachmentsPerEvent` | `4` | 媒体展开时的原始附件上限，超出部分保留摘要 |
| `media.maxAttachmentsPerRequest` | `8` | 工作窗口在一次请求中重发的原始附件总数上限 |
| `media.maxAttachmentMbPerRequest` | `6 MB` | 原始附件总体积上限，按 Base64 体积计算；单个过大的媒体不注入 |

每个事件首次渲染时冻结媒体内容与预算决策。新媒体超出请求预算时保留原位的身份和摘要，并请求记忆压缩；不会为了容纳新图而淘汰、替换较早的历史图片。成功压缩后才开始新的预算窗口。服务端明确拒绝某种输入模态时，只停用对应模态；音频格式错误只尝试一次正常整理以淘汰旧编码输入，不停用音频或牵连视频。无关的 400 不触发媒体降级。整理失败保留原始经历并重试，不静默重写已经发送过的媒体前缀。413 仍暂时停用原始附件并整理上下文，应核对附件预算及模型服务、反向代理的请求体上限。

### 媒体发送

QQ 的 OneBot/NapCat 链路将已标记的表情包发送为 `image` 段中的 `sub_type: 1`，这是图片表情的协议形式；普通图片不带此标记，`summary` 只是预览文字。发送边界会在 Koishi 元素转换完成后恢复 `sub_type`，避免它被改写为 NapCat 不识别的 `subType`。这里发送的是图片表情，不会还原商城表情的专属 `mface` 身份；其他平台的原生表情支持取决于其适配器。

Bot 不只能收，也能发：

- **发图/发视频**：`send` 的 `media` 参数使用明确引用（如 `media: ["media:12", "gallery:照片/猫.png"]`），在正文末尾追加。图文混排则在 `msg` 原位置写 `第一张 <media ref="media:12"/> 第二张 <media ref="media:27"/>`。表情包按平台要求可能独立成消息，但与前后文字、其他图片的顺序保持一致；
- **选择与发送分开**：`pick_media(media)` 只解析所选媒体，返回可用于发送的明确引用，不创建草稿、不自动发送。内容不确定时先 `view_media` 查看，再用一次完整的 `send` 提交；旧槽位与按图片序号发送的协议已停用，错误引用不会静默变成普通文本发送；
- **按表达需要选用**：已有明确引用且内容清楚时可以直接发送，需要查找时使用 `check_gallery` 或只读的 `check_media`。
  收藏夹按 `表情包 / meme / 截图 / 照片 / 未整理` 分类，自己的选用备注与图片识别、表情的可能用途分别显示。
  备注按文件哈希校验关联，不代表原发送者的意图。表情优先根据想表达的回应、适用或易误读的语境选择，
  无需点评画面、宣布收藏或另外解说。拿不准内容时才 `view_media`，表情细看复用用途缓存，不再追加画面赏析请求。
  普通内容摘要与表情用途缓存分开，同一素材可以有不同用途；显式图库引用保留相应分类的发送方式。
  确实想留作以后复用时可用 `gallery_save` 指定分类并记录个人备注，收藏不是发送前置步骤；需要移除时用 `gallery_remove`；
- **用户投放**：用户可以直接把文件丢进 `basePath/gallery/未整理/`（或 gallery 根目录，会被自动
  清扫进未整理），**无须自己写描述、做分类**。未整理内容不会被转成待办；需要管理时才使用 `gallery_move`，
  备注可选，同分类也能更新备注；
- **发送范围**：当前角色工具通过 `send` 发送文字、图片与视频；`send_file`、`send_voice`
  已不在角色工具列表中。选中的音频会明确说明不能通过当前 `send` 发送，不引导调用已移除的工具。

发送遵循当前耗时配置；启用 `bot.ignoreSendDuration` 时忽略发送耗时。`cancel` 只阻止尚未提交的发送，最终以平台回执为准。
发出的媒体以内部引用入库，之后通过 `read_channel` 回看时仍按同一媒体身份与原位顺序呈现。
duration 明显超过按字数估算的打字时间时，视为"过会儿再发"而非打字耗时：
不自动发出，到点询问 Bot 是否要发（详见「时间模型」），延期期间的三种打断条件也会以事件告知。
发送结果区分已确认发送、部分发送、提交前拦截和送达未知。平台已确认的发送不会因为后续本地记录、
聊天回看或设备刷新失败而变成“未发送”；超时或缺少回执时先核对记录，不自动缩短或整条重发。

回复目标使用 `reply_to`：接受完整平台消息 ID、`msg:ID` 或 `(msg:ID)`，保留字母、符号和负号，不从文字中抽取数字。`media:12` 和 `msg:12` 属于不同命名空间，不能互换。无效引用、冲突的引用标签或旧 `images` 等发送参数会明确阻止发送；未启用引用能力时也不会静默改成普通消息。

另外两条拟人化约束：

- **消息长度**：Prompt 要求完整、自然地表达新内容，避免把已发送的意思换说法再发。`msg` 超过
  `messaging.longMessageChars`（默认 100 字符）时，本次调用不会提交到平台；确需这些内容可加
  `confirm_long: true` 确认。拦截提示只针对本次调用，不否认之前的发送回执；
- **频道 id 纠错**：Bot 把频道 id 写错时（如把用户名当频道 `onebot:TouchNight`），插件会用
  已知频道的参与者模糊匹配，**不执行发送**，而是以事件提示正确的频道 id 让它下次填对。

### 指令消息与外部自发消息

- 他人发送的**指令消息**（如 `world.status`）与普通消息一视同仁：照常入库、按通知策略投递给
  Bot（指令本身也照常执行，互不影响）；
- `messaging.externalSelfMessages`（默认 `off`）控制 Bot 账号发出的、**非本插件产生**的消息
  （其他插件的输出、Koishi 指令回复，以及适配器上报的其他登录设备所发消息）是否让 Bot-LLM 看到：
  - `simulate`：可由 `send` 表达的消息按真实媒体引用记录为自己的工具调用，结果保留图文顺序、摘要与原图；
    音频等无法由 `send` 表达的消息记录为自己的实际行动感知，避免伪造不可执行的工具参数；
  - `event`：以事件告知"你的账号发出了一条消息，但那不是你发的"——Bot 知情但不认领；
  - `silent`：不做任何通知，只是像普通消息一样入库（发送者是 Bot 自己的账号）——
    等 Bot 之后翻看聊天记录（`select_channel`）时自己"意外发现"；
  - 除 `off` 外，这类消息都会入库，`select_channel` 可回看；仅接受平台成功回执或已收到的账号消息，
    被拦截、取消或未确认的发送不会被伪装成成功消息。本插件发送与其他插件并发发送按实际调用归属区分，
    平台回声按账号、频道与消息 ID 去重。其他设备的消息能否被发现取决于适配器是否上报账号自身消息。
- `messaging.selfCommands` 让平台确认成功的纯文本消息按裸指令名（不带前缀）触发其他 Koishi 指令。
  使用本账号的真实权限与原消息 ID，指令结果可按上述模式回流。带图片、引用等组合内容不自动执行指令；
  `world` 管理指令及其别名、插值和嵌套执行始终排除，指令输出本身不会再次自动执行。

**撤回感知**：别人撤回一条消息时（包括群管理员撤别人、对方撤自己的消息），消息记录里对应那条会被
改写为 `[某某 撤回了一条消息]` 标记（Bot 已看过的上下文不动——它自然记得内容，只是知道"这条被收回
去了"）；Bot 正关注该频道时会追加一条事件告知。消息与撤回按同频道顺序处理，慢图片不会在撤回后重新出现。
来自本账号的撤回也可能由其他设备发起；没有操作归属证据时只陈述账号发生了撤回，不把它认作自主意图。
